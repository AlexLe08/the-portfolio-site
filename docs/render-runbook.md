# Render (Backend hosting)

Render hosts the FastAPI backend as a Docker-based web service, deployed
from `render.yaml` (a Render "Blueprint" — infrastructure as code, same
idea as the GitHub Actions workflows).

The deployed service is at https://portfolio-backend-leto.onrender.com
(`/health` for a liveness check, `/docs` for the interactive API docs).
`/health` also returns `commit`, the Git SHA of the running deploy, read
from `RENDER_GIT_COMMIT`, which Render sets on every deploy (it is not in
`render.yaml`). It is `null` outside Render. Compare it with the merge
commit to tell whether a deploy has gone live.

## Why Render, specifically

Same requirement as Neon: no way to be charged without deliberately
upgrading. Render's free tier is a fixed $0 instance type, not a metered
one — there's no overage billing mechanism for a free-tier service at all.
The only way this service would ever cost money is explicitly changing its
instance type to a paid one. The trade-off: the service spins down after
15 minutes of inactivity and takes roughly 30–50 seconds to wake up on the
next request. Acceptable for a low-traffic portfolio site.

## Initial setup

1. Push `render.yaml` (repo root) to GitHub — Render's Blueprint flow reads
   this file directly.
2. render.com → New → Blueprint → connect the repo. Render detects
   `render.yaml` and shows the one service it defines.
3. Fill in the prompted environment variables (see table below) and click
   Apply.

## Environment variables

Defined in `render.yaml`, but values are set in Render's dashboard, not
the file — this keeps secrets out of git while still version-controlling
which variables exist.

| Variable | Source | Notes |
|---|---|---|
| `ENVIRONMENT` | hardcoded `production` in render.yaml | — |
| `DATABASE_URL` | Neon connection string, pasted manually | `sync: false` in render.yaml — Render prompts for it once, won't overwrite it on future deploys |
| `ADMIN_API_KEY` | auto-generated by Render | `generateValue: true` — view the actual value in the dashboard when making an authenticated admin request |
| `JWT_SECRET` | auto-generated by Render | `generateValue: true` (a base64 256-bit value). Signs the session tokens from `POST /auth/login`. Tokens are stateless, so regenerating this value is how to log out every session early. Must be at least 32 bytes, or the service fails at startup |
| `ADMIN_PASSWORD_HASH` | output of `backend/hash_password.py`, pasted manually | `sync: false`, and added after the Blueprint was created, so Render won't prompt for it: set it in the dashboard. Paste the hash with no quotes (quotes are only needed in a local `.env`). Admin login answers `503` until both this and `JWT_SECRET` are set; the admin key works either way. All login attempts share one limit (`LOGIN_RATE_LIMIT`, default 5 per `LOGIN_RATE_WINDOW_SECONDS`, 900), because logins arrive through the frontend's server and so all have the same address. To change the password, generate a new hash and replace this value |
| `ALLOWED_ORIGINS` | the Vercel production URL, pasted manually | set after the frontend is deployed (see `docs/vercel-runbook.md`); update this if the Vercel production domain ever changes |
| `DISCORD_WEBHOOK_URL` | Discord webhook URL, pasted manually | `sync: false` in render.yaml. Create it in Discord under channel settings > Integrations > Webhooks. Optional: when empty or unset, contact-message notifications are skipped. Each submission posts one embed (the message limit is 4000 characters so it fits Discord's 4096-character embed description). Delivery failures never fail the request (the message is already saved in Postgres either way) and are logged as `Discord notification failed: HTTP <status> <Discord's response>` when Discord rejects the call, or `... failed: <ErrorType>` for network errors. An `HTTP 401` ("Invalid Webhook Token") or `404` means the URL in Render is wrong or the webhook was deleted or regenerated: re-copy it from Discord, with no quotes or spaces. A GET on the URL (`curl -s -o /dev/null -w "%{http_code}\n" "<url>"`) returns 200 when it is valid. An `HTTP 429 [HTML page: ... Cloudflare ...]` line is different: Cloudflare, which fronts Discord, is blocking the service's shared outbound IP, so the URL is fine. This is outside the app's control; a redeploy may land on a different IP |
| `RESEND_API_KEY` | Resend API key, pasted manually | `sync: false` in render.yaml. Create it in the Resend dashboard under API Keys. Optional: email is skipped unless both this and `NOTIFY_EMAIL_TO` are set. Email goes through Resend's HTTP API because Render's free tier blocks outbound SMTP (ports 25, 465, 587). Failures are logged as `Email notification failed: HTTP <status> <Resend's response>` and never fail the request |
| `NOTIFY_EMAIL_TO` | the address that receives contact messages | `sync: false`. Without a verified Resend domain, this must be the email on your Resend account (the `onboarding@resend.dev` test sender can't send anywhere else; a `403` "You can only send testing emails to your own email address" means they differ). Each email sets `reply_to` to the visitor, so replying goes straight to them. `EMAIL_FROM` (default `Portfolio Contact <onboarding@resend.dev>`) is optional; set it only after verifying a domain in Resend |
| `CLIENT_IP_HEADER` | request header naming the visitor, e.g. `CF-Connecting-IP` | Optional but needed in production. `POST /contact` allows 5 messages per hour per visitor (`CONTACT_RATE_LIMIT`, `CONTACT_RATE_WINDOW_SECONDS`). These and the `LOGIN_RATE_*` values must be at least 1, or the service fails at startup. Behind Render's proxy the socket address is the proxy's, so without this every visitor shares one limit. Only name a header the platform overwrites, because a caller can forge any other and dodge the limit. Cloudflare rejects client-supplied copies of `CF-Connecting-IP`, so for this header the condition holds. Verify the limiter after changing it; see "Verifying the rate limit" below. The limiter is in-memory: it resets on restart and isn't shared across instances |
| `SENTRY_DSN` | Sentry project DSN, pasted manually | `sync: false`. Optional: error reporting is off when empty. See "Error reporting (Sentry)" below |
| `CLOUDINARY_URL` | Cloudinary "API environment variable", pasted manually | `sync: false`, and added after the Blueprint was created, so set it in the dashboard. Optional: media uploads are off when empty. Copy it from Cloudinary Console > Settings > API Keys, using a key generated for production (e.g. `portfolio-backend-render`), not the local one, so either can be revoked alone. The value is `cloudinary://<api_key>:<api_secret>@<cloud_name>` with no quotes and no `CLOUDINARY_URL=` prefix; anything else fails at startup with "CLOUDINARY_URL must look like ..." (the secret is never printed) |

## Error reporting (Sentry)

Unhandled errors (500s) are reported to Sentry, tagged with
`ENVIRONMENT` and the deploy's commit (`RENDER_GIT_COMMIT`) as the
release. 4xx responses are not reported. Setup and the privacy settings
are in `backend/app/core/monitoring.py`: request bodies, local
variables, IP addresses, and cookies are never sent, and headers whose
name contains `auth` or `key` are filtered.

Free tier: the Developer plan (1 user, 5k errors a month, 30-day
history). Sentry's pricing page says data over the quota is dropped and
not billed. Signing up asked for no payment method (2026-10-23). If
Sentry ever asks for one to stay on the free plan, stop and find another
option.

Setup:
1. sentry.io: sign up on the Developer plan, then create a project with
   the FastAPI platform. Copy its DSN (Settings > Projects > Client Keys).
2. Check the DSN from your machine: put `SENTRY_DSN=...` in
   `backend/.env`, then from `backend/` run
   `./.venv/bin/python -c "import sentry_sdk; from app.core.monitoring import init_sentry; init_sentry(); sentry_sdk.capture_message('Sentry setup check'); sentry_sdk.flush()"`.
   The message shows up under Issues within a minute, with environment
   `development`. Remove the line from `.env` afterwards unless you want
   local errors reported too.
3. Render dashboard: set `SENTRY_DSN` on the service. Render won't
   prompt for it, because it was added after the Blueprint was created.
   Saving it redeploys the service.

Linking stack traces to GitHub (a code mapping): the container runs the
code from `/app`, so a frame's path starts with `app/` (for example
`app/routers/contact.py`), while in the repo the same file is under
`backend/app/`. A code mapping tells Sentry to swap that prefix, so each
frame links to its line on GitHub. Suspect commits need it too.
1. Check for an existing mapping first. With the GitHub integration
   installed, Sentry tries to create mappings for Python projects
   automatically. In Sentry, open Settings > Projects >
   `portfolio-backend` > General Settings and look under Connected
   Repositories.
2. If there's none: click Connect repository there (the project is
   preselected) and pick `AlexLe08/the-portfolio-site`. If the repo
   isn't listed, give the Sentry app access to it on GitHub first:
   Settings > Integrations > GitHub > Configure.
3. Fill in:
   - Branch: `main`. Sentry uses it when an event's release isn't linked
     to a commit, which is the case here: the release is set to the
     commit SHA, but no commits are uploaded to Sentry.
   - Stack trace prefix: `app/`
   - Repository prefix: `backend/app/`
   The form's example preview should rewrite `app/main.py` to
   `backend/app/main.py`. An empty stack trace prefix matches every
   file, so don't leave it empty.
4. Check it on the first real error: an in-app frame should link to the
   file on GitHub. If it doesn't, open the event's JSON (the `{}`
   button) and compare a frame's `filename` with the prefix. The
   `capture_message` test above has no stack trace, so it can't test
   the mapping.

Suspect commits only appear for issues created after the integration
was set up, and only for commits less than a year old. Sentry's code
mappings docs: https://docs.sentry.io/integrations/source-code-mgmt/code-mappings/

## Verifying the rate limit

Run this after changing `CLIENT_IP_HEADER` or anything about the limiter.
Every request sets the honeypot field, so nothing is saved or sent. The
first request can take 30-50 seconds if the service is asleep.

```sh
API_URL=https://portfolio-backend-leto.onrender.com
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "request $i: %{http_code}\n" -X POST "$API_URL/contact" \
    -H 'content-type: application/json' \
    -d '{"name":"a","email":"a@b.co","message":"hi","website":"x"}'
done
```

Expect five `201`s, then `429` with `Retry-After` of about an hour. This
blocks your own connection (including the real contact form) for that
hour, so run it when you can afford that.

Two things to know about how Render is set up:

- **A forged `CF-Connecting-IP` can't be tested, and can't be used.**
  Cloudflare, which fronts Render, rejects a request that carries that
  header from the client: `403` with body `error code: 1000`, before it
  reaches the app. So the header the app sees is the one Cloudflare sets,
  not one a caller chose. Don't add a forged-header step to this check; it
  only ever returns `403`.
- **The loop alone can't tell "per visitor" from "everyone shares one
  key".** If `CLIENT_IP_HEADER` were unset, the key would be the proxy's
  address and the 6th request would still return `429`. To rule that out,
  after the loop blocks you, send one more honeypot request from a
  different network (a phone on cellular, for example). `201` means each
  visitor has their own limit. `429` means they share one: check that
  `CLIENT_IP_HEADER` is set on the Render service.

Status: verified against production on 2026-10-21. The loop gave five
`201`s, then `429` with `Retry-After: 3585`. The blocked connection showed
the form's "too many messages" error, and a real message sent from a
different network (VPN) went through, so each visitor has their own limit.

## Free-tier limitations hit during setup, and the workarounds

These are specific to the free plan and worth knowing if this service is
ever upgraded — several of the workarounds below would become unnecessary.

**No `preDeployCommand`.** Render rejects a Blueprint that sets this field
on a free-tier service — it's a paid-plan-only feature for running a
command after build but before traffic switches to the new version.
Workaround: migrations run as part of the container's own startup command
instead, chained before the server starts:

```dockerfile
CMD ["sh", "-c", "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]
```

This runs `alembic upgrade head` on every container start, including every
free-tier sleep/wake cycle — safe because the command is idempotent (it
no-ops if there's nothing new to migrate). The real trade-off: if a
migration fails, it fails at container startup rather than in a dedicated
pre-deploy step. Render's own health-check-gated rollout still protects
against a broken deploy going live — a container that never starts
successfully never passes `/health`, so Render keeps the previous working
version serving traffic — but the failure surfaces in deploy logs rather
than a dedicated, clearly-labeled pre-deploy failure.

**No shell access.** Also a paid-plan feature. One-off commands (seeding
data, an ad-hoc query) have to be run from a local machine against the
Neon database directly — see `docs/neon-runbook.md`.

**`$PORT` is dynamic, not fixed.** Render assigns the service a port at
runtime via the `$PORT` environment variable (commonly 10000, not the
locally-familiar 8000). The Dockerfile's `CMD` uses shell form
specifically so `${PORT:-8000}` actually expands; the exec-array form
(`["uvicorn", "--port", "8000"]`) would pass the literal string
`${PORT:-8000}` to uvicorn with no shell to interpret it.

## Redeploys

Automatic on every push to `main` (once CI passes and the PR merges — see
`docs/ci-cd-runbook.md`), and automatic whenever an environment variable is
changed and saved in the dashboard. No manual redeploy step needed in
either case.
