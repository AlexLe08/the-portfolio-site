# Render (Backend hosting)

Render hosts the FastAPI backend as a Docker-based web service, deployed
from `render.yaml` (a Render "Blueprint" — infrastructure as code, same
idea as the GitHub Actions workflows).

## Why Render, specifically

Same requirement as Neon: no way to be charged without deliberately
upgrading. Render's free tier is a fixed $0 instance type, not a metered
one — there's no overage billing mechanism for a free-tier service at all.
The only way this service would ever cost money is explicitly changing its
instance type to a paid one. The trade-off: the service spins down after
15 minutes of inactivity and takes roughly 30–50 seconds to wake up on the
next request. Acceptable for a low-traffic portfolio site.

## Initial setup

1. Push `render.yaml` (repo root) to GitHub — Render's Blueprint flow reads
   this file directly.
2. render.com → New → Blueprint → connect the repo. Render detects
   `render.yaml` and shows the one service it defines.
3. Fill in the prompted environment variables (see table below) and click
   Apply.

## Environment variables

Defined in `render.yaml`, but values are set in Render's dashboard, not
the file — this keeps secrets out of git while still version-controlling
which variables exist.

| Variable | Source | Notes |
|---|---|---|
| `ENVIRONMENT` | hardcoded `production` in render.yaml | — |
| `DATABASE_URL` | Neon connection string, pasted manually | `sync: false` in render.yaml — Render prompts for it once, won't overwrite it on future deploys |
| `ADMIN_API_KEY` | auto-generated by Render | `generateValue: true` — view the actual value in the dashboard when making an authenticated admin request |
| `ALLOWED_ORIGINS` | the Vercel production URL, pasted manually | set after the frontend is deployed (see `docs/vercel-runbook.md`); update this if the Vercel production domain ever changes |
| `DISCORD_WEBHOOK_URL` | Discord webhook URL, pasted manually | `sync: false` in render.yaml. Create it in Discord under channel settings > Integrations > Webhooks. Optional: when empty or unset, contact-message notifications are skipped. Each submission posts one embed (the message limit is 4000 characters so it fits Discord's 4096-character embed description). Delivery failures never fail the request (the message is already saved in Postgres either way) and are logged as `Discord notification failed: HTTP <status> <Discord's response>` when Discord rejects the call, or `... failed: <ErrorType>` for network errors. An `HTTP 401` ("Invalid Webhook Token") or `404` means the URL in Render is wrong or the webhook was deleted or regenerated: re-copy it from Discord, with no quotes or spaces. A GET on the URL (`curl -s -o /dev/null -w "%{http_code}\n" "<url>"`) returns 200 when it is valid. An `HTTP 429 [HTML page: ... Cloudflare ...]` line is different: Cloudflare, which fronts Discord, is blocking the service's shared outbound IP, so the URL is fine. This is outside the app's control; a redeploy may land on a different IP |

## Free-tier limitations hit during setup, and the workarounds

These are specific to the free plan and worth knowing if this service is
ever upgraded — several of the workarounds below would become unnecessary.

**No `preDeployCommand`.** Render rejects a Blueprint that sets this field
on a free-tier service — it's a paid-plan-only feature for running a
command after build but before traffic switches to the new version.
Workaround: migrations run as part of the container's own startup command
instead, chained before the server starts:

```dockerfile
CMD ["sh", "-c", "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]
```

This runs `alembic upgrade head` on every container start, including every
free-tier sleep/wake cycle — safe because the command is idempotent (it
no-ops if there's nothing new to migrate). The real trade-off: if a
migration fails, it fails at container startup rather than in a dedicated
pre-deploy step. Render's own health-check-gated rollout still protects
against a broken deploy going live — a container that never starts
successfully never passes `/health`, so Render keeps the previous working
version serving traffic — but the failure surfaces in deploy logs rather
than a dedicated, clearly-labeled pre-deploy failure.

**No shell access.** Also a paid-plan feature. One-off commands (seeding
data, an ad-hoc query) have to be run from a local machine against the
Neon database directly — see `docs/neon-runbook.md`.

**`$PORT` is dynamic, not fixed.** Render assigns the service a port at
runtime via the `$PORT` environment variable (commonly 10000, not the
locally-familiar 8000). The Dockerfile's `CMD` uses shell form
specifically so `${PORT:-8000}` actually expands; the exec-array form
(`["uvicorn", "--port", "8000"]`) would pass the literal string
`${PORT:-8000}` to uvicorn with no shell to interpret it.

## Redeploys

Automatic on every push to `main` (once CI passes and the PR merges — see
`docs/ci-cd-runbook.md`), and automatic whenever an environment variable is
changed and saved in the dashboard. No manual redeploy step needed in
either case.
