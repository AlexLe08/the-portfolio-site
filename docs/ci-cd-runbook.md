# CI/CD and branch protection

Two independent GitHub Actions workflows, plus a branch ruleset on `main`
that requires both to pass before merging — the same "CI enforced
structurally" pattern used on the Discord bot project.

## Workflows

| File | Job name | Runs | Checks |
|---|---|---|---|
| `.github/workflows/backend.yml` | `test` | every PR and push to `main` | installs backend deps, runs `alembic upgrade head` against a throwaway SQLite file, runs `pytest` |
| `.github/workflows/frontend.yml` | `build` | every PR and push to `main` | `npm ci`, `npm run lint`, `npm run build` (which includes a full TypeScript check — see note below) |

Both workflows run on **every** PR, regardless of which half of the
monorepo it touches. See "Why no path filters" below for why that's
deliberate, not an oversight.

### Why `build`, not a separate `tsc` step, is what catches type errors

`next build` runs its own TypeScript check internally as part of the
build. An earlier version of `frontend.yml` ran a standalone
`npx tsc --noEmit` step before `build`, which failed with
`Cannot find name 'LayoutProps'` — that type is generated by Next.js into
`.next/types/` during `build`/`dev`, so checking before it exists fails
for a reason that has nothing to do with real type errors. Fixed by
removing the standalone step entirely and relying on `build`'s own check,
in the correct order.

## Why no `paths:` filters on the workflow triggers

Both workflows originally used `paths:` filters (e.g. `frontend/**`) so a
backend-only PR wouldn't waste CI time running the frontend job, and vice
versa. This created a real bug: a **required** status check that never
runs (because its path filter didn't match) never reports a status at
all — GitHub shows it as "Expected — waiting," indefinitely, with no way
to distinguish "irrelevant, ignore it" from "still running." A PR touching
only one half of the repo would be permanently unmergeable.

The fix was to remove the `paths:` filters and let both jobs run on every
PR. At this repo's scale (jobs take seconds), the CI-time cost of running
both every time is negligible compared to the complexity of the "correct"
fix at larger scale — a `dorny/paths-filter`-style action that makes the
*job* always run and report a status, while conditionally skipping the
expensive *steps* inside it based on what changed. Worth revisiting if
either job's runtime grows enough to matter.

## Branch ruleset (`main`)

GitHub → repo → Settings → Rules → Rulesets. Configuration used:

- **Enforcement**: Active
- **Target branches**: `main`
- **Require a pull request before merging**: on — without this, the
  required-checks rule below can be bypassed entirely by pushing straight
  to `main`.
- **Require status checks to pass**: on, with both `test` and `build`
  added as required checks.
- **Require branches to be up to date before merging**: off — mostly
  useful for a merge-queue setup with frequent concurrent PRs; costs extra
  CI re-runs for no real benefit on a solo repo.

**Known gotcha**: the required-check picker references checks by their
**job id** from the workflow YAML (`test`, `build`), not the workflow's
display name (`Backend CI`, `Frontend CI`). Renaming a `jobs:` key or
restructuring a workflow silently breaks the ruleset's reference — the PR
would then show no required checks at all, not an error. Worth a quick
check of the ruleset page after any workflow restructuring.

A required check can also only be selected once GitHub has recorded at
least one real run of it — so after any workflow change (new job name,
new workflow file), push once and let it run before trying to reference it
in the ruleset.
